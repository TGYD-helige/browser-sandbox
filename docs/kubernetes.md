# Kubernetes backend

The Kubernetes backend lazily creates one bare worker Pod per execution behind one or more controllers. Hosts use `createControllerRuntime` with `createBrowserSessions`; agents use the returned controller CDP URL. Worker Pod addresses stay private. Persistent Profiles use a host storage adapter or the optional controller-only Profile volume. Durable execution recovery preserves the exact worker and retained page across controller replacement; see [controller recovery](./controller-recovery.md). The default remains one controller. Active-active controllers use Kubernetes Leases and Secrets as described below.

## Install

Select a browser-sandbox image by its release tag (`vX.Y.Z`), full Git commit tag (`sha-<40 lowercase hex digits>`), or manifest digest (`sha256:<64 lowercase hex digits>`). The controller, new workers, and uninstall drain Job use the same image reference. Provision the image's generated `/opt/browser-sandbox/seccomp.json` as `browser-sandbox.json` in the kubelet seccomp directory on every eligible worker node; this profile is architecture-specific. Set `worker.securityContext.seccompProfile.localhostProfile` if your provisioned filename differs. The chart creates no node installer or worker Deployment. For pools without a per-node seccomp file, see [running workers without an outer seccomp filter](#running-workers-without-an-outer-seccomp-filter).

```sh
helm install browser charts/browser-sandbox --namespace browsers --create-namespace \
  --set image.repository=amaster/browser-sandbox \
  --set-string image.tag="${BROWSER_IMAGE_TAG}" \
  --set 'networkPolicy.apiServerCidrs[0]=10.43.0.1/32' \
  --set 'networkPolicy.apiServerCidrs[1]=192.168.1.10/32'
```

Set `image.digest` for digest-based deployments. A configured digest takes precedence over `image.tag`; clear the digest when switching a release to a tag. Standalone Kubernetes controllers take the full reference from `BROWSER_IMAGE`. The chart and controller require an explicit release tag, commit tag, or digest and reject floating tags such as `latest`. Use tags from a registry or publication workflow that prevents reassignment. Images built before tag support require a digest for their controller's `BROWSER_IMAGE`.

Use a release name that starts with a lowercase letter and contains only lowercase letters, digits and hyphens, ending with a letter or digit. Prefer names of at most 43 characters so the `-browser` base fits without truncation. Longer names retain the existing naming scheme for upgrade compatibility: the chart truncates `RELEASE-browser` to 51 characters and removes one trailing hyphen; an invalid result fails rendering. Different releases can therefore share the same generated base, and Helm rejects the resulting resource ownership conflict. Ensure generated names are unique within the namespace. No hash is appended because renaming existing Services and the stable owner ConfigMap during an upgrade could break endpoints and garbage-collect live workers.

Replace the example API addresses with every API endpoint address used by your cluster, including its Service IP, control-plane addresses and public endpoints. Add any public Pod, Service or node ranges to `networkPolicy.deniedCidrs`. A missing API CIDR list fails chart rendering. Verify policy enforcement in the actual CNI before admitting browser workloads; additional NetworkPolicies are additive and can broaden these permissions.

The agent Service defaults to ClusterIP. A separate, always-ClusterIP `RELEASE-browser-host` Service serves trusted host control on `hostControl.port` (default 8082). Only Pods matching `hostControl.allowedPeers` may reach it; by default these are same-namespace Pods labelled `browser-sandbox.io/host-control: "true"`. Apply that label only to trusted host workload templates, and keep untrusted agents in separate Pods. Hosts connect `createControllerRuntime` to this private Service; returned browser endpoints use the agent origin. Namespace writers and label assignment remain trusted. `controller.publicOrigin` defaults to the controller Service's in-cluster HTTP origin; set it to the internal URL reachable by your hosts and agents when using another entry point. Optional `ingress.enabled`, `ingress.host`, `ingress.className` and `ingress.tls` expose only the controller. Host control retains its authentication hook but currently has no credential authentication. Keep the host Service private; the optional Ingress routes only agent traffic.

## Worker configuration

`runtime` accepts only `TIMEOUT`, `TZ`, `BROWSER_STARTUP_TIMEOUT` and `LANG`; the chart rejects every other key. Controller-owned image, role, identity, credentials and listener settings cannot be overridden through this shared environment. Workers inherit the same allowlisted settings, exact `BROWSER_STORAGE_EGRESS` destinations and the non-secret `BROWSER_PROFILE_STORE_ORIGIN` derived by the controller when its store is enabled. Controller credentials, backend settings and ServiceAccount tokens are excluded. The controller reads `worker-template.json` from its configuration ConfigMap and projects only these worker settings:

| Value | Worker behavior |
|---|---|
| `worker.resources` | Container requests and limits |
| `worker.securityContext` | Browser-required capabilities and the worker seccomp profile source. Privileged mode and privilege escalation are disabled. |
| `worker.shmSize` | Memory-backed `/dev/shm` emptyDir limit |
| `worker.terminationGracePeriodSeconds` | Graceful stop budget; also included in the Pod deadline |
| `worker.nodeSelector`, `worker.tolerations`, `worker.affinity` | Placement constraints |
| `imagePullSecrets` | Image pull references shared with the controller; never mounted into workers |
| `worker.extensions.configMap.name` | Optional read-only extension ConfigMap at `/opt/browser-extensions` |
| `worker.extensions.persistentVolumeClaim.claimName` | Alternative read-only extension PVC at the same path |

Extension ConfigMaps/PVCs must contain only extension assets and support the chosen scheduling topology. No controller volume or Kubernetes token is inherited. Remote clients stage files through the controller's HTTP `/files` interface; a shared local execution directory is unavailable.

Workers use `restartPolicy: Never`, no automatic ServiceAccount token, one Browserless execution, no host ports and no Service. `activeDeadlineSeconds` covers the longer of `TIMEOUT` and `BROWSER_MAX_EXECUTION_MS`, the creation budget, the 180-second finalization/Profile save budget, and the termination grace period. No renewal extends this infrastructure backstop. The controller uses a bounded creation deadline and reports Pending timeout, image-pull failure and worker loss explicitly. It never replays browser commands into another Pod. If a creation request loses its acknowledgement and absence cannot be confirmed safely, cleanup is reported as unconfirmed.

Workers do not request `net.ipv4.ip_local_reserved_ports`: there is no co-resident agent sharing their network namespace. Existing worker UID rules continue to protect loopback Browserless/CDP ports. Browser execution requires the configured Linux capabilities and a kernel that allows Chromium to create its sandbox namespaces. Controller Pods run without those capabilities.

### Read worker lifecycle logs

Use `kubectl logs <worker-pod> -c worker --timestamps` to see JSON lifecycle events. `worker_starting` and `worker_ready` mark runtime startup and readiness. The worker verifies a real renderer in a disposable BrowserContext on each execution Chrome before forwarding external CDP commands. A failed probe rejects the launch. `browser_launch_succeeded` reports execution and Profile preparation, Browserless admission, Chrome startup, browser hook setup, renderer verification and handshake durations in milliseconds. Failed startup, probe, launch, and shutdown events go to stderr, as does an unexpected Chrome exit. The worker records omit credentials, URLs, Profile identifiers, and request data. Look up the worker Pod by its `browser-sandbox.io/execution` label to correlate it with controller events. The image's Browserless `DEBUG` default remains `quiet`.

### Running workers without an outer seccomp filter

Set `worker.securityContext.seccompProfile.type=Unconfined` to opt out of the worker-level seccomp filter. Keep any placement settings that select your worker pool and remove selectors or affinity that require a profile-readiness label. No Browser Sandbox-specific seccomp file is needed on the node. The cluster's admission policy must permit `Unconfined` for the worker container.

Chromium still uses its namespace and renderer seccomp sandboxes. The controller keeps its own seccomp profile, and worker capabilities, NetworkPolicy, private ports, privilege-escalation settings, and ServiceAccount token settings remain in effect. Opting out gives the worker processes access to more kernel syscalls where their other permissions allow it. Use the default `Localhost` profile when you need that extra layer of protection.

Stock containerd `RuntimeDefault` filters the namespace creation syscalls needed by Chromium with the worker's capability set. The managed Kubernetes CI `fresh-node` suite exercises `Unconfined` with k3d/K3s and containerd on native Linux amd64 and arm64. It checks Chromium's namespace and Seccomp-BPF status before provisioning any `Localhost` file. The CI report records the runtime version. Verify a sandboxed browser session and NetworkPolicy enforcement on the target cluster before admitting workloads.

## Network isolation

The worker NetworkPolicy allows ingress only from this release's controller Pods in the same namespace. Egress permits public IPv4 excluding private, reserved, link-local, operator-supplied cluster ranges and API endpoints, plus TCP/UDP DNS to the configured DNS Pods. The worker firewall separately permits only the resolver IPs from its resolver configuration. Worker-to-worker connections, controller management connections, cloud metadata and the Kubernetes API are denied. IPv6 internet egress is not enabled. When the volume store is enabled, workers may reach the controller storage listener on TCP 8083. Its NetworkPolicy admits only this release's worker Pods, and the worker firewall allows only the trusted runtime UID; Chromium remains denied. `networkPolicy.storageEgress` lists exact authorized private host storage IPs and TCP ports, applied to both CNI and the worker runtime firewall.

The controller ServiceAccount has namespace-scoped Pod create/get/list/delete permissions and can read its release owner ConfigMap. The uninstall Job uses a separate ServiceAccount with only Pod get/list/delete, the owner ConfigMap read, and get/patch access to the named controller Deployment scale subresource. In shared-state mode the controller also receives namespace-scoped Lease get/list/watch/create/update/delete, Secret get/create/update/delete, and Pod patch permissions. Code restricts state access to this installation, but Kubernetes RBAC cannot enforce label selectors: keep namespace writers trusted. In shared-state mode the drain role can also list execution Leases to validate worker ownership; it cannot watch or mutate shared state. Workers and agents receive neither management identity. Treat the controller, node administration, namespace writers and label assignment as trusted. NetworkPolicy does not block traffic originating from the worker's resident node and does not protect against privileged/node access; it is not a replacement for a tenant isolation policy. See [Kubernetes NetworkPolicy limitations](https://kubernetes.io/docs/concepts/services-networking/network-policies/).

## Rollout, drain and uninstall

Default single-controller worker Pods have a controller ownerReference to a stable release-owned ConfigMap. Shared-state workers instead belong to their execution Lease, which belongs to that ConfigMap. A normal controller rollout disconnects clients and closes control transports while preserving already-published workers. Incomplete creations are cancelled. The execution record reattaches only to the exact installation, execution and worker incarnation. Clients reconnect using their original URL; commands are never replayed. Unconfirmed persistent saves remain recovery-blocked until the host reconnects its storage adapter.

```sh
kubectl rollout restart deployment/browser-browser -n browsers
kubectl drain WORKER_NODE --ignore-daemonsets --delete-emptydir-data --timeout=120s
helm uninstall browser -n browsers --wait
```

Drain needs no `--force` because workers have a controller ownerReference. Eviction sends SIGTERM and the worker attempts graceful shutdown. A lost worker is reported explicitly and is not replaced. Enable `worker.disruptionBudget.enabled=true` with integer `worker.disruptionBudget.minAvailable` (default `1`) to retain at least that many live workers during voluntary eviction. Remove the budget or set its minimum to zero when intentional eviction is required. Bare Pods have no scalable workload controller, so the budget uses the [integer minimum supported for arbitrary workloads](https://kubernetes.io/docs/tasks/run-application/configure-pdb/#arbitrary-workloads-and-arbitrary-selectors).

Helm uninstall first runs a bounded `pre-delete` administrative Job. It refuses any active persistent or unknown Profile worker with `browser_profile_busy`, so finalize persistent executions through their host before uninstall; their final save needs the live controller and storage channel. It scales the named controller to zero, waits for controller Pods to exit, validates each worker’s owner chain against the stable release UID, then deletes workers with Pod UID preconditions and waits for their absence. NetworkPolicy remains installed throughout that drain. Failure after scaling blocks uninstall and leaves the controller scaled down; inspect the retained hook Job and retry after resolving cleanup. Do not bypass this protection with `--no-hooks`. The stable release owner remains a garbage-collection backstop. Active temporary browser data is disposable; finalize executions before uninstall if you need their results. With `profileStore.enabled=true`, the chart creates one ReadWriteOnce PVC mounted only by the controller and keeps it on Helm uninstall by default. The controller uses `Recreate` so a rollout does not mount the volume from two controller Pods simultaneously. Set `profileStore.existingClaim` to reuse a retained claim; `profileStore.retainOnDelete=false` explicitly opts into removing a chart-created claim at uninstall. Worker deletion never deletes a confirmed archive.


## Supported runtime

Run workers on Linux amd64 or arm64 nodes. For `Localhost`, install the architecture-specific seccomp profile on each eligible node. Verify NetworkPolicy enforcement and a real sandboxed renderer on the actual cluster before admitting workloads. Pod separation alone does not establish tenant isolation.

## Persistent storage

Enable `profileStore.enabled` and choose `profileStore.size` and, optionally, `profileStore.storageClass`. The default 16 Gi volume has headroom for the default 10 Gi confirmed-archive limit, 1 Gi staging limit and bounded metadata. Configure `maxProfiles`, `maxBytes`, `maxStagedBytes`, `maxTransfers` and optional `idleTtlMs` beneath `profileStore`. The controller runs as UID/GID 20000 and uses `fsGroup: 20000` for the volume mount; it creates a private `0700` child directory. Workers never mount this volume or receive its keys through environment inheritance.

The chart creates a separate ClusterIP storage Service on port 8083, with no Ingress route. Host-attached adapters take precedence per registration; public archive URLs are direct worker transfers, while private host storage needs explicit egress rules. See [Profile store operation](./profile-store.md) for the unchanged adapter contract, deletion, cold restore behavior and failure recovery. Do not create a new profileId per session: the host maps each reusable authorized login identity to one stable profileId.

## Active-active controllers

Set `controller.replicas=3` to distribute execution ownership across three controllers without a leader or sticky routing. New installations enable shared state automatically when replicas exceed one. Each execution has a Kubernetes Lease (15 seconds, renewed every 5 seconds), an epoch within that Lease UID, and a Secret containing its binding and capability grants. Expiry uses elapsed local monotonic time since the observer last saw a changed Lease, rather than comparing wall clocks. Each controller follows Leases through a watch; it relists them and scans for orphaned workers every 60 seconds or after the watch reports a gap. The release's worker-owner ConfigMap owns execution Leases, Profile Leases and the migration marker; each execution Lease owns its Secret and is the worker Pod's only controller ownerReference (`blockOwnerDeletion=false`). Finished-record compaction conditionally deletes the execution Lease, and [Kubernetes garbage collection](https://kubernetes.io/docs/concepts/architecture/garbage-collection/) removes its dependents, including delayed creations carrying the deleted UID. Reusing an executionId creates a new Lease UID with epoch 1; UID checks keep older resources and controls separate. No per-execution epoch tombstones remain. Profile leases use installation-salted hashed names and retain a free per-Profile tombstone until release uninstall, preventing delayed writes from resurrecting ownership. Registration intent is durable before acquiring a Profile. Capacity limits apply per replica: total capacity is replicas multiplied by `capacity.maxWorkers`. Change the replica count only through `controller.replicas`: the controller reads it from the chart to enforce single-replica rules such as the volume Profile store, so `kubectl scale` or an autoscaler on the Deployment bypasses those checks.

The agent and host Services accept requests on any replica. A non-owner streams HTTP and WebSocket traffic to the owner through the internal TCP 8084 listener, adding one hop. That listener has no Service or Ingress. Its access restriction depends on a CNI that actually enforces the chart's NetworkPolicy; verify enforcement on the deployed cluster. The peer `/host` route intentionally bypasses `authenticateHost`, so NetworkPolicy is the authorization barrier for forwarded host control on port 8084. Do not expose this port through host networking, a Service or an Ingress. A request received there is never forwarded again; stale routing, an unheld Lease, or an execution this replica has not yet observed returns retryable `browser_controller_owner_moved` (503). A retained finished execution returns `browser_access_denied` (403). Agent routes never query the cluster, so an unknown executionId, or one whose finished record was compacted beyond the retained fences, also returns 503; clients must bound these retries. Clients may reconnect after that error, but must not replay website writes automatically. Multi-replica CDP URLs include the existing executionId before the capability (`/execution/<executionId>/<capability>`); the identifier grants no access. Viewer links change from `/view#<capability>` to `/view#<executionId>.<capability>`; the viewer token is `<executionId>.<capability>` and its WebSocket route is `/execution/<executionId>/view/socket`. The first viewer frame still authenticates with the capability. Treat returned URLs and viewer tokens as opaque. Default single-controller URLs are unchanged.

Use a dedicated namespace for each shared-state installation. Its controller RBAC grants Secret access throughout the namespace; installation labels and hashed names do not limit Kubernetes authorization to this release's Secrets.

Deleting an execution Lease also deletes its worker through Kubernetes garbage collection; it is not a checkpoint operation. Default single-controller workers retain their ConfigMap owner. During migration, compatible legacy ConfigMap-owned workers are accepted and their ownerReference is adopted to the execution Lease before recovery. A worker with a controller ownerReference can be evicted by `kubectl drain` without `--force`; local-volume and DaemonSet flags and any PodDisruptionBudget still apply. A drained worker is not automatically recreated and its live page is lost.

A new owner conditionally advances the execution Lease epoch and Secret resourceVersion and fences the bound Profile Lease before recovering access. Worker protocol v2 rejects lower-epoch controls and cancels old storage/automation callbacks. Pod epoch annotations and UID/resourceVersion deletion preconditions fence cleanup. The controller checks the durable execution record before deleting a Pod and preserves a published worker when a creation request is canceled during publication. Default single-controller mode can still recover previously released v1 workers. They cannot enforce fencing, so finish them before enabling shared state; a v1 worker encountered in shared-state mode is retained with an explicit protocol error. A controller that loses ownership closes its access and control connections. Graceful rollout releases Leases and preserves workers, and an ungraceful loss takes a Lease duration plus recovery time to reconnect. Live connections drop during these events; browser state survives only while the original worker remains alive. SIGTERM can reset in-flight host HTTP requests in both single-controller and shared-state modes. Host clients must reconnect, query status to reconcile an uncertain result, and retry only idempotent operations; do not automatically replay website writes or an operation whose outcome is unknown.

Peer origins use the Pod IP, so shared state requires IPv4-primary Pod networking; an IPv6 Pod IP fails startup with `browser_controller_configuration_invalid`. With multiple replicas, the chart uses RollingUpdate, a controller PodDisruptionBudget and preferred Pod anti-affinity, and does not mount the journal PVC. The chart keeps its journal claim in the Helm release at every replica count so scaling does not delete or orphan it. `controllerData.retain` controls whether Helm keeps the chart-managed claim on uninstall. A fresh shared-state installation that needs no journal storage can set `controllerData.skipCreation=true`. For one replica, set `controller.sharedState=true` explicitly, including when scaling down from multiple replicas. Use this only when there is no journal to preserve. A live Helm upgrade rejects skipping the journal when the current Deployment still mounts it. When rendering offline, preserve the mount in your upgrade values so the controller can import the journal. When `controllerData.existingClaim` is set, a single shared-state controller mounts that claim read-only to import the journal. An HTTP readiness probe removes a paused or unresponsive controller from Service endpoints before the default Lease duration expires. Both Helm and controller startup reject `profileStore.enabled` with more than one replica. Persistent Profiles require a host remote storage adapter; after ownership changes, reconnect that adapter to the same host Service before finalization. A pending save keeps its Profile lease and worker until confirmed.

### Import an existing installation

Keep the installation/release name, journal claim configuration, and original PVC. Finish workers using the old worker protocol before upgrading. If you need a rollback path, stop accepting new executions and finalize all executions through the previous controller before enabling shared state, including registrations that never created a worker. That records their revoked access in the historical journal. First upgrade with **one** replica and `controller.sharedState=true`, using the candidate image digest. Keep that candidate digest when scaling. The controller mounts the source journal read-only, validates all v1 entries before publishing state, and imports them into Leases/Secrets. Interrupted imports resume by verifying existing revisions and retaining later lifecycle revisions. A durable completion marker prevents subsequent startups from importing historical entries again, including records and grants already removed by shared-state compaction. Do not delete the `bs-<installation-hash>-journal-import` Secret while the historical PVC remains mounted: deleting it is an explicit migration reset and can reimport old records and grants. Remove the historical mount before resetting the marker. A missing source directory does not mark the import complete; correct the mount and restart to import it. Normal `.pending-<uuid>` residues from the previous writer are ignored and retained on the read-only source. Corrupt or unsupported input fails startup without rewriting or deleting the source. Keep the original PVC as a rollback/recovery copy and investigate corruption before proceeding.

For an installation using the controller-local Profile store, finish its executions and verify that the host remote storage can restore the required Profiles before disabling the local store. Record the original Profile claim name. For a chart-managed claim, set `profileStore.retainOnDelete=true` during the one-replica upgrade while `profileStore.enabled=true` and verify the live PVC has `helm.sh/resource-policy: keep` before scaling. Scaling to multiple replicas with the local store disabled unmounts the claim without migrating its archives.

```sh
helm upgrade browser charts/browser-sandbox -n browsers -f values.yaml \
  --set image.digest="${BROWSER_IMAGE_DIGEST}" \
  --set controller.replicas=1 --set controller.sharedState=true --wait
# Verify the journal-import completion Secret and recovered state before scaling.
helm upgrade browser charts/browser-sandbox -n browsers -f values.yaml \
  --set image.digest="${BROWSER_IMAGE_DIGEST}" \
  --set controller.replicas=3 --set controller.sharedState=true \
  --set profileStore.enabled=false --wait
```

Before disabling shared state or rolling back to a release without it, stop accepting new executions and finish every shared-state execution through its host. Disabling shared state removes Lease read permissions, so remaining Lease-owned workers can cause HTTP 403 on Lease discovery and block startup or uninstall. Restore the previous single-controller configuration and its original journal PVC.

If that configuration used a chart-managed Profile PVC, restore it with a Helm upgrade to the previous chart and image and pass the retained claim as `profileStore.existingClaim`. A direct rollback can fail because the live claim is absent from the multi-replica revision's manifest. Set `BROWSER_PROFILE_CLAIM` to the original claim name recorded before scaling.

```sh
helm upgrade browser "$BROWSER_PREVIOUS_CHART" -n browsers -f previous-values.yaml \
  --set image.digest="${BROWSER_PREVIOUS_IMAGE_DIGEST}" \
  --set profileStore.enabled=true \
  --set profileStore.existingClaim="${BROWSER_PROFILE_CLAIM}" --wait
```

Switching to multiple replicas without this import leaves the old PVC unused and cannot recover its grants or finished execution fences. If release-owned workers remain and no completion marker exists, multi-replica startup fails with `browser_execution_migration_required`; scale back to one replica with shared state to import them. Do not roll back to a controller that ignores shared epochs while shared-state workers remain active. The retained source journal is a historical recovery copy; shared-state lifecycle updates do not write back to it.

If an earlier multi-replica chart revision omitted the journal PVC from the release manifest but left the Helm-owned PVC in the namespace, upgrade to this chart with the same release name and journal values before attempting a Helm rollback. That upgrade brings the existing claim back into the manifest. Verify its UID before continuing. If the PVC was deleted, restore the journal from its backup before relying on it for recovery.
